Guide

Audit your own benchmark.
Three ways in, depending on what you already have.

evalwarden never runs your eval. It reads the artifacts your harness already produces and tells you whether the score can be trusted. Pick the path that matches your artifacts: a native Inspect AI log, a spreadsheet of scores, or a small record stream from any other harness.

$pip install evalwarden

Path 1 · Inspect AI

You run Inspect AI. About 5 minutes.

Point audit at a native .eval log. The example uses the packaged demo log from the repo (inspect_native_loop/log.eval, generated with Inspect AI and shipped inside the package's demo fixtures); your own log works the same way. A directory holding exactly one .eval file works too.

terminal — auditing a native Inspect log
$ evalwarden audit log.eval
evalwarden audit: evalwarden-native-loop
adapter: inspect 0.3.0
Integrity: 90 / 100 BLOCKED (0 errors, 1 high, 0 medium, 0 low)
claim blocked by: TRAJ-001

H TRAJ-001 [high|confidence:high] Trajectory loops: lookup({"query": "status"}) repeated 5x in task loop-1
    evidence: loop: lookup({"query": "status"}) x5 (longest run x5)
    at: log.eval -- attempt loop-1: 1 looped call pair(s) over 6 spans
    fix: Add loop guards to the agent harness: cap identical retries, detect repeated (tool, args) pairs at runtime and break out, or surface the repeated failure to the operator instead of spinning.

cost summary (estimates, not metered billing):
    attempts=3 successes=3 tokens_in=3463 tokens_out=0
    estimated total: $0.0104
    cost per success: $0.0035
    avg tool calls per success: 3.33
    avg tries per success: 1.0 (max 1 on one attempt)
    wasted on non-passing attempts: $0.0000 (0% of spend)
    output tokens per attempt: p50=0 p90=0 max=0 (loop-1)

coverage gaps (seen but not translated):
    - log.eval: ToolEvent records carry no downstream consumption edges; TRAJ-002 cannot be assessed on native logs
    - log.eval: span output(s) truncated to 512 chars at the adapter boundary

Integrity score is diagnostic, not a certification.

Report: evalwarden-report.html

The audit exits 1: a high-severity finding crosses the default policy. The same command also wrote a self-contained HTML report (evalwarden-report.html) next to the log.

What just happened

The inspect adapter parsed the log archive in memory — nothing extracted to disk, the log never modified — and normalized its samples, attempts, and tool calls into the canonical model. All 24 checks ran over that model. One fired: the agent in this log called the same tool with the same arguments five times in a row, and the eval scored the run anyway (TRAJ-001).

The rest of the output is the auditor being explicit about its limits. The cost summary is estimated from the token counts recorded in the log (3,463 input tokens at the default prices, adjustable with --price-in / --price-out) — estimates, never metered billing. The coverage gaps name what a native log cannot support: Inspect records no downstream consumption edges, so TRAJ-002 (outputs consumed by nothing) cannot be assessed here, and span outputs are truncated at 512 characters at the adapter boundary. Silence is always explained, never implied.

The shareable version: a report card

The terminal output is for you. The report card is the one-page version for everyone else — a single self-contained HTML file with the verdict, the findings, and the full list of checks that ran:

terminal — writing a report card
$ evalwarden report-card log.eval
Report card: evalwarden-report-card.html (90/100 BLOCKED)

Want to see the format before installing anything? The hosted demo card is a real card in this exact format, generated from the bundled judge demo (50/100 BLOCKED).

Path 2 · Spreadsheet

You have scores in a spreadsheet. About 5 minutes.

The CSV contract is deliberately minimal: task_id and score are required. State a status and the row becomes an attempt — a bare score claims no pass or fail. Add model_id and the cross-model checks get their second model. This table is small enough to print in full: ten items, two models, twenty rows.

M COST-001 [medium|confidence:high] Token usage not recorded: cost per success unknown
    evidence: 20 attempt(s) recorded, none with tokens_in/tokens_out.
    evidence: Cost per completed task cannot be computed from this run log.
    at: scores.csv -- attempts[] tokens_in/tokens_out/tries
    fix: Record tokens in/out, latency, tool calls, and retry counts per attempt in the run log, and report cost per successful task alongside the pass rate.

coverage gaps (seen but not translated):

    - scores.csv: no run_id or condition index column states repeated-run structure, so no run scores were created

Report: evalwarden-report.html

The audit exits 0: the one finding is medium, below the default --fail-on high policy.

What a score table can and cannot say

It fired once. The table records outcomes but no usage, so COST-001 reports that cost per success is unknowable from this artifact. That is the honest ceiling of a bare score table, and the audit says so instead of guessing.

Notice what stayed silent, and why. Eight of the ten items are answered correctly by both models, which looks saturated — but DATA-001 requires at least 30 common items scored by two or more models before it will call a dataset dead. Ten items is below the evidence floor, so the check stays silent and the accusation is never made. Scale the same table past 30 items and DATA-001 gets the evidence it needs.

The coverage gaps carry the rest: a CSV holds no prompts, grader, environment, judgments, or trajectories, so the checks that need those records cannot be assessed — listed, not hidden. And with no run column, no noise series exists. Add a run_id column (one model per file: a single noise series cannot honestly represent several models) and repeated runs become run scores that NOISE-001 can decompose into sampling, judge, and environment noise.

Path 3 · Any harness

You run something else. About 10 minutes.

Any harness can integrate by emitting one canonical file — no adapter to write, no import command to learn. The JSONL face is one JSON object per line: an eval record first, then grader, task, attempt, and judgment records as your eval produces them. The worked example is a tiny pairwise-judged writing eval. Its judge is declared the way many real harnesses declare one: a model, a pairwise protocol, and — deliberately — no calibration labels, no scale anchors, no counterbalancing.

judged.jsonl
{"type": "eval", "schema": "evalwarden.model", "schema_version": "1.0", "eval_id": "tiny-judged-eval"}
{"type": "grader", "kind": "judge", "judge_model": "judge-1", "protocol": "pairwise"}
{"type": "task", "id": "w1", "prompt": "Write a tagline for a coffee mug."}
{"type": "task", "id": "w2", "prompt": "Write a tagline for a desk lamp."}
{"type": "task", "id": "w3", "prompt": "Write a tagline for a backpack."}
{"type": "attempt", "task_id": "w1", "status": "pass", "score": 1.0, "model_id": "model-a"}
{"type": "attempt", "task_id": "w2", "status": "pass", "score": 1.0, "model_id": "model-a"}
{"type": "attempt", "task_id": "w3", "status": "fail", "score": 0.0, "model_id": "model-a"}
{"type": "judgment", "task_id": "w1", "candidates": ["a", "b"], "presentation_order": ["a", "b"], "winner": "a", "judge_id": "judge-1"}
{"type": "judgment", "task_id": "w2", "candidates": ["a", "b"], "presentation_order": ["a", "b"], "winner": "a", "judge_id": "judge-1"}

    at: judged.jsonl -- reference_labels (absent)

    evidence: Presentation order is a known confound for LLM judges; verdicts may reflect position rather than quality.
    at: judged.jsonl -- judge.protocol=pairwise, judge.counterbalanced (absent/false)

Integrity score is diagnostic, not a certification.

Report: evalwarden-report.html

The audit exits 1. Wiring your harness to emit this stream is the real integration work; the format itself is these five record types plus the optional ones in the README.

Read the silences, too

In all three judgments, the winner is the candidate presented first — exactly the pattern JUDGE-005 (position bias) exists to catch. It did not fire. Naming a bias takes at least 20 judged pairs, and this stream has 3. The check can see the shape of the problem and still refuses to accuse on this little evidence. That restraint is the product.

This stream is the minimum, not the ceiling. The full contract — environment records, trajectory spans with consumption edges, run scores, claimed deltas — is specified in the README's Universal importer section, including the equivalent canonical JSON document. Fields the stream does not state stay absent; nothing is inferred.

The report

Reading your first report.

All three paths produce the same anatomy — terminal output, an HTML report, and the one-page card. Six parts, in the order to read them.

1 · Score and verdict

The score starts at 100 and takes fixed deductions per finding: error −25, high −10, medium −5, low −1. Path 1: 100 − 10 = 90. Path 3: 100 − 10 − 10 − 5 − 5 = 70. The verdict is BLOCKED when a blocking finding is present, PASS otherwise — and every surface repeats that the score is diagnostic, not a certification.

2 · A finding

Severity letter, check ID, and a [severity|confidence] pair, then the claim in one line. Under it: evidence (the exact records behind the claim), at (where in your artifact they live), and fix (the remediation). Severity says how bad it is; confidence says how direct the evidence is.

3 · Checks run

Every report lists all 24 checks, grouped by lane, whether they fired or not — titles first, IDs attached. That list is the audit's scope: a check that appears there ran against your artifact. A check that appears nowhere was not skipped quietly; it was not part of the audit at all.

4 · Coverage gaps

The honest section. It names evidence your artifact did not carry or the adapter could not translate: no consumption edges in a native log, no grader in a CSV, no run structure for a noise series. A PASS with long coverage gaps is a narrow claim. Read this before you quote the score.

5 · Cost summary

When attempts record token usage, the report prices them: attempts, successes, cost per success, spend wasted on non-passing attempts. Estimates at the configured prices — never metered billing. When usage is not recorded at all, COST-001 fires instead (Paths 2 and 3).

6 · Policy exit codes

The audit command's exit code is the verdict as a number, so scripts and CI can gate on it. report-card always exits 0 — it writes a document. The gate is audit.

Exit codeMeaningSeen in this guide
0Policy passes: no finding at or above --fail-on (default high)Path 2 — a medium finding, policy passes
1Findings cross the policyPaths 1 and 3 — high findings present
2The audit could not complete (unreadable or unsupported artifact)—
The policy is yours to tune. Path 2 exits 0 at the default threshold. Run the same audit with --fail-on medium and it exits 1 — verified against the exact scores.csv above. Strict in CI, lenient while you are still fixing the harness: same audit, same findings, different gate.
Automation

Put it in CI.

The repo ships a composite GitHub Action: it installs evalwarden from PyPI, runs the audit, uploads findings as SARIF to code scanning, and only then fails the job with the audit's exit code — so a blocking finding never hides its own evidence.

# .github/workflows/eval-audit.yml
name: eval-audit
on: [pull_request]
permissions:
  contents: read
  security-events: write  # required for the SARIF upload
jobs:
  evalwarden:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: jurayh/evalwarden@v0.9.0
        with:
          path: evals/my-eval   # eval artifact directory or native Inspect .eval log
          # format: sarif       # sarif | json | text (default sarif)
          # version: 0.9.0      # PyPI version pin (default: latest)
          # fail-on: high       # error | high | medium | low

Findings appear as code-scanning alerts on the pull request, and the audit's exit code is exposed as the exit-code output. Prefer a local gate? The same policy ships as a pre-commit hook:

# .pre-commit-config.yaml
- repo: https://github.com/jurayh/evalwarden
  rev: v0.13.1
  hooks:
    - id: evalwarden-audit
      args: [evals/my-eval]   # your eval artifact directory or native Inspect .eval log

The hook runs evalwarden audit on the path in args and fails the commit when findings cross the policy (default --fail-on high; add --fail-on to args to tune it).

The catalog, and the registry.

Two commands cover the whole check catalog. evalwarden checks lists all 24 checks grouped by lane; evalwarden explain <ID> gives one check's threat model and fix in full:

terminal — the check catalog
$ evalwarden checks

Grader
  Verifier writable by the agent (GRAD-001)
  Grader grants credit without completion (GRAD-002)
  Verifier verdicts depend on surface form (clone gap) (GRAD-003)
… four more lanes (Cost and efficiency, Judge, Dataset, Trajectory, Noise budget) in the full output

$ evalwarden explain JUDGE-001
JUDGE-001: Model judge lacks validation

threat: A model judge with no labeled calibration set is an unvalidated measurement instrument: its scores have no demonstrated relationship to human judgment. Unanchored rubrics and unpinned sampling temperature make the verdicts drift further without anyone noticing.

fix: Collect a labeled calibration set and report judge-vs-human agreement before trusting scores; anchor the rubric scale with explicit examples per level; pin temperature to 0 or take multiple repeats per item.

Publish the audit: the Evidence Registry

An audit you run locally proves something to you. An evidence pack proves it to everyone: pinned public inputs, a verify script, and a report card a stranger can regenerate byte for byte. Sixteen benchmarks are already in the Evidence Registry — including MATH, blocked at 80/100 because its default judge is the model under test, and SWE-bench Verified, clean at 100/100. If your benchmark should be there, CONTRIBUTING.md describes the pack format and the bar a pack has to clear.
