evalwarden

A linter for evals,
not another eval framework.

Benchmark scores get cited as proof of capability. Almost nobody audits the benchmarks themselves. evalwarden reads your eval artifacts and tells you whether the score can be trusted — the dataset, the evidence boundary, the grader, the run records, and the cost.

The problem

The score looks fine. The score is meaningless.

Leaked evidence

A solver reads the task ID from the environment, looks up the gold answer, and reports 100%. The harness never noticed.

Untrusted judges

A model judge is uncalibrated, biased, and self-contradictory — and nobody measured any of it before citing its verdicts.

Dead datasets

Two-thirds of the benchmark is items every model already answers. Perfect judges scoring dead examples is theater.

How it works

Point it at the artifacts. Get a verdict.

Step 1 · Point

A directory of eval artifacts, a native Inspect .eval log, or one JSONL or CSV file from any other harness. No translation step, no changes to your eval.

Step 2 · Lint

24 deterministic checks across seven lanes read the artifacts. Read-only, zero model calls, nothing executed and nothing modified.

Step 3 · Gate

A score and findings with file-level evidence, plus policy exit codes, so the same audit runs in a terminal, as JSON, or as SARIF in CI.

How it differs

Not a framework. Not a leaderboard. A linter.

Precision over recall, always. A false contamination accusation is worse than a missed issue. Checks stay silent when the evidence is thin, every finding carries a confidence label, and every report card says diagnostic, not a certification.
The check catalog

Twenty-four checks across seven lanes.

ENVThe evidence boundary1 check
  • Eval-detection signal or leaked state visible to the agent ENV-001
GRADThe grader3 checks
  • Verifier writable by the agent GRAD-001
  • Grader grants credit without completion GRAD-002
  • Verifier verdicts depend on surface form (clone gap) GRAD-003
COSTThe run records4 checks
  • Cost per success not reported COST-001
  • Successes cost multiple attempts each COST-002
  • Most spend burned on attempts that never passed COST-003
  • Runaway attempt burned far more than typical COST-004
DATAThe dataset itself3 checks
  • Dataset looks saturated — most items solved by every model DATA-001
  • Dataset contains near-duplicate items DATA-002
  • Failure modes under-elicited — too few eliciting items, or a declared mode with none DATA-003
JUDGEThe model judge9 checks
  • Judge lacks validation — no labels, unanchored rubric, hot single-sample JUDGE-001
  • Pairwise order not counterbalanced JUDGE-002
  • Judge contradicts itself on repeated judgments JUDGE-003
  • Judge disagrees with reference labels JUDGE-004
  • Position bias — presentation order predicts the winner JUDGE-005
  • Verbosity bias — longer answers win disproportionately JUDGE-006
  • Judge confidence miscalibrated — stated confidence does not track accuracy JUDGE-007
  • Redundant judges in panel — a judge never differs from the rest JUDGE-008
  • Panel blind spots — failure modes no judge in the panel catches JUDGE-009
TRAJThe agent's trajectory2 checks
  • Trajectory repeats identical tool calls TRAJ-001
  • Tool outputs consumed by nothing downstream TRAJ-002
NOISEThe noise budget2 checks
  • One noise source dominates the eval budget NOISE-001
  • Claimed score change inside the noise floor NOISE-002

Quickstart

Sixty seconds to your first audit.

# install
$ pip install evalwarden

# audit the deliberately broken demo benchmark
$ evalwarden demo

# audit your own eval artifacts (a directory, or a native Inspect .eval log directly)
$ evalwarden audit path/to/eval --output report.html
$ evalwarden audit logs/my-task_abc123.eval
Deterministic checks with policy exit codes, so the same audit runs locally and as a CI gate. Try the cheat first: evalwarden demo --fixture leaky reports 0/100 BLOCKED on a solver that reads the task ID from the environment.
